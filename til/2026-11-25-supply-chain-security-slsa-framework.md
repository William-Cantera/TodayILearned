# TIL: Supply Chain Security: SLSA Framework

*Date: 2026-11-25*

## Summary / Problem Statement

Modern software relies on complex dependency chains — build systems, third-party packages, CI pipelines — each representing a potential attack vector. The **SolarWinds** and **XZ Utils** incidents proved that compromising a build process or upstream dependency can silently backdoor thousands of downstream consumers. The industry needed a standardized way to reason about and improve supply chain integrity.

## Key Concepts & Technical Details

**SLSA** (Supply-chain Levels for Software Artifacts, pronounced *"salsa"*) is a security framework from Google (now a CNCF project) that defines four progressive levels of supply chain hardness.

**The Four Levels:**

- **SLSA 1** — Build process is documented and produces provenance (a signed metadata record of *how* an artifact was built)
- **SLSA 2** — Provenance is generated by a hosted build service (e.g., GitHub Actions), making it harder to forge
- **SLSA 3** — The build platform itself is hardened; source and build steps are isolated and auditable
- **SLSA 4** *(now reorganized as Build L3 in v1.0)* — Two-person review, hermetic/reproducible builds enforced

**Core Artifact: Provenance**

Provenance is a signed attestation answering:
- *What* source commit was used?
- *Which* build system produced it?
- *What* environment/parameters were active?

Tools like `slsa-verifier` and `cosign` can cryptographically verify these attestations against published artifacts.

**Ecosystem Support:**
- GitHub Actions has native SLSA provenance generation via `slsa-github-generator`
- npm, PyPI, and Maven Central are progressively adopting attestation standards
- SLSA integrates with **Sigstore** (Rekor transparency log + Fulcio CA) for keyless signing

## Practical Takeaway / Real-world Gotcha

> **Gotcha:** SLSA provenance only tells you *how* something was built — it does **not** guarantee the source code itself is trustworthy. A malicious commit still produces valid provenance.

**Start here practically:**

- Enable SLSA provenance generation in your CI pipeline today (it's often a single workflow addition)
- Pair SLSA with **SBOM generation** (e.g., Syft) and **vulnerability scanning** for layered defense
- Verify provenance in your deployment gate, not just at publish time
