# TIL: OAuth 2.0 PKCE Flow Mechanics

*Date: 2026-11-23*

## Summary / Problem Statement

When building public clients (SPAs, mobile apps) that can't securely store a client secret, the standard OAuth 2.0 Authorization Code flow is vulnerable to **authorization code interception attacks**. PKCE (Proof Key for Code Exchange, pronounced "pixie") was designed specifically to close this gap without requiring a shared secret.

---

## Key Concepts & Technical Details

PKCE adds a cryptographic challenge/verifier pair to the standard auth code flow:

**Setup (before redirecting the user):**
- Generate a cryptographically random string called the **`code_verifier`** (43–128 characters, URL-safe)
- Derive a **`code_challenge`** from it:
  ```
  code_challenge = BASE64URL(SHA256(ASCII(code_verifier)))
  ```
- Send `code_challenge` + `code_challenge_method=S256` with the initial authorization request

**Redemption (exchanging the code for tokens):**
- Send the original `code_verifier` (never sent before) in the token request
- The authorization server independently hashes it and compares against the stored challenge
- If they match → tokens are issued; if not → request is rejected

**Why this works:**
- An attacker who intercepts the authorization code never saw the `code_verifier`
- The `code_challenge` is a one-way hash — it can't be reversed to recover the verifier
- Each flow uses a **fresh, unique** verifier/challenge pair

---

## Practical Takeaway / Real-world Gotcha

> **Always use `S256`, never `plain`.**

The `plain` method (where `code_challenge == code_verifier`) offers almost no protection — it only defends against passive eavesdroppers, not active attackers. Most modern authorization servers reject `plain` outright.

**Additional gotchas to watch for:**
- **Verifier entropy matters** — use `crypto.getRandomValues()` or a secure RNG, never `Math.random()`
- **Don't reuse verifiers** — generate a fresh pair per authorization attempt; reuse can enable replay attacks
- **Store the verifier in session/memory only** — avoid `localStorage` where XSS can reach it
- PKCE is now recommended for **all** OAuth clients, not just public ones (per RFC 9700)
